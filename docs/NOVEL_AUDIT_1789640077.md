**后果**：`_generate_outline_batch` / `generate_outline_continuation` 都靠

### 2.3 🔴🔴 思维链（CoT）污染了 **6 处** 记忆层（最严重）

本作最严重的缺陷：**模型的推理过程被当成成品落盘**。

| # | 文件 | 内容实测 | 应为 |
|---|---|---|---|
| 1 | `summaries/chapter_00001_summary.txt` | 1789 字符，以 `我们需要回答用户："请生成摘要（100-200字）："…` 开头 | 100–200 字摘要 |
| 2 | `memory/chapters/chapter_00001.txt` | 1782 字符，**同一段 CoT** | 权威摘要 |
| 3 | `memory/global_summary.txt` | 140 字符 = **CoT 内部第 4 版草稿原文** | 全书概述 |
| 4 | `memory/timeline/timeline_000.json` | `event` 字段 = CoT 文本 | 故事事件 |
| 5 | `memory/chunks/page_0000.json` | `type:"plot"`，payload = CoT | 情节块 |
| 6 | `memory/index.json` / `scores.json` | 键 = `plot_1789640553243`（CoT 块的 id） | 摘要块 id |

**根因**（`git show bbb8332^:app/novel_agent.py` 的 `finalize_chapter`）：

```python
summary = content[:200]
result = self.ai.chat(
    [{"role": "user", "content": f"请生成摘要（100-200字）：\n{content[:2000]}"}],
    system="你是故事摘要助手。",
    max_tokens=1000,          # ← ① 恰好等于 reasoning.THINKING_MIN_TOKENS
)
if result:                    # ← ② 无任何校验
    summary = result
    self.memory.save_chapter_summary(chapter_num, summary)
```

**两条叠加**：

- **① `max_tokens=1000` 恰好等于 `THINKING_MIN_TOKENS`**，而阈值判据是**严格小于**
  ⇒ 思考**没有被禁用**，但预算又不够输出 `content` ⇒ 框架**兜底返回 `reasoning_content`**；
- **② `if result:` 不做任何内容校验** ⇒ CoT 被当作摘要直接落盘。

**为什么危害极大**：`memory_manager.get_recent_summaries()` 读的就是
`memory/chapters/chapter_*.txt`，而它会被注入**每一章的上下文**。
⇒ **CoT 会作为"历史摘要"回灌给后续章节的生成**，形成自我污染的正反馈。
本作只有 1 章所以后果未显现，但**第 2 章起会持续恶化**。

> 本条已在 `bbb8332` 修复：`max_tokens=2000` + `thinking_enabled=False`
> + `_looks_like_chain_of_thought()` 校验 + 异常时弃用回退正文截断。

### 4.2 【表观完好 vs 结构性空洞】——这是本次审计最关键的区分

| 维度 | 判定 | 依据 |
|---|---|---|
| **句子完整性** | ✅ 完好 | 末句 `天柱之上，云层翻涌如沸。` 以句号收束，无截断 |
| **表层收束** | ✅ 有 | 主角"归我吧"表态 + 留续集钩子（黎照霜上石阶） |
| **情节闭环** | 🔴 **无** | 结尾场景的核心道具 **`玄元之心` 不在 `outline.json` 里** |
| **结构完整性** | 🔴 **无** | 章节由 **4 个 `---` 分段**拼成（行 201 / 313 / 457），`药谷 → 九霄宫 → 天柱 → 玄元之心` 四段跳跃 |

**🔴 关键判据**：`outline.json`（唯一正确的大纲）第 1 章的 summary 是：

> 药奴陆昭被沉入魔鼎池底等死…**噬尽她千年修为与帝印精血**。拂晓持帝印踏出池畔，
> 号令九霄宗俯首，**三日收服三十六国，半月镇压九幽魔渊，一月内登临天下共主，诸天仙王跪伏称臣**。

而**正文结尾落在"玄元之心 / 万源归一"**——**这是大纲里根本没有的东西**。
⇒ 结尾不是按大纲写的，而是**分段续写链在"该结束了"的地方自行发明的一个收束点**。

### 4.3 烂尾成因（4 条机制，本版**必然发生**）

#### 机制①　`word_count > 3000` 强制走分段流水线 ⇒ "结尾"只是第 4 段的分段收束

`novel_agent.py:784/1002`：`word_count > 3000` 时路由到 `_generate_long_chapter`。
本作 `word_count=10000` ⇒ **必然分段**。

`_generate_long_chapter`（`novel_agent.py:2291`）：
- `seg_size = 2000`，`part_count = min(ceil(10000/2000), 8) = 5`（实测正文 4 段）
- **最后一段**的提示词固定为：
  > *"这是本章最后一段，请推进剧情约{seg_size}字并给出自然完整的段落结尾。严禁重复。"*

🔴 **要害**：提示词要的是 **"自然完整的段落结尾"**（段落级），
而不是 **"故事结尾"**（全书级）。模型忠实地照做了——它给了**这一段的**结尾。

⇒ **所谓"烂尾"，本质是"把段落收束误当成了故事收束"。**
这是一个**提示词层级错误**，不是模型能力问题。

#### 机制②　审校者与修订者**看不到全文**，却被要求"不少于 15459 字"

```python
# _reviewer_evaluate (novel_agent.py:1091)
sample = content[:2000] + "\n...（中间省略）...\n" + content[mid-500:mid+500] \
       + "\n...（中间省略）...\n" + content[-1000:]
```

⇒ **审校者从未见过连续的整章**；它只能看到"开头 2000 + 中间 1000 + 结尾 1000"。

而 `_writer_revise`（`:1175`）：
```python
needed_tokens = max(8192, int(original_len * 2.5))   # ≈ 26000+
prompt: "输出完整的修订后文本（不少于{original_len}字）"
guard:  if len(response) < original_len * 0.5: return original
```

**诊断日志直接证明模型意识到了矛盾**（seq 43 / 49 / 55 的 `reasoning_content`）：
> *"原文（共15459字）但显示中间省略很多…要求输出完整修订文本，不少于15459字"*

⇒ **审校/修订环节对结尾毫无保护作用**：它看不到结尾的上下文，也无法在修订中保持结尾。
更糟的是：修订被要求"不少于原文长度"，模型只能**灌水**。

#### 机制③　字数门禁用 `len(content)`（含标题与换行）⇒ 虚高放行

`_has_excessive_repetition`（`novel_agent.py:1324`）：
```python
actual_words = len(content)     # ← 字符数，含 '#' 标题、换行符、全角标点
```

**实测**：`chapters/chapter_0001.txt` = **10654 字符**，其中
- 汉字 **8760**（占 82.2%）
- 其余 1894 字符 = 标题 + 换行 + 标点

⇒ 相对 10000 字目标，`10654/10000 = 106%` **轻松过关**，
但**真实汉字量只有 87.6%**。字数门禁**被格式字符注水**，无法起到"写够了吗"的把关作用。

#### 机制④　末段"补全补丁"在真实收束后追加了一段不相干内容

`novel_agent.py:2367-2401`：若 `len(result)>500` 且最后一个有效字符不在
`{。！？…"」】—.!?~…}` 中，则**另起一次 `ai.chat`（`max_tokens=1000`）**要求：
> *"补充一个自然的收尾（20-60字）"*

然后去重后**追加**到 `result` 末尾。

**实测命中**：正文第 **555** 行 `黎照霜望向天柱顶端那点幽光，按剑道："上去看看，是谁在拽这口井。"`
位于第 10202 字符（全长 10654）——**正好是补丁的位置**。

**诊断日志 seq 37** 的 `reasoning_content` **逐字预测了这句话**：
> *"我们需要续写，20-60字，自然收尾…'黎照霜望向天柱顶端那点幽光，按剑道："上去看看，是谁在拽这口井。"'"*

🔴 **更糟的是**：日志 seq 40（审校）显示审校模型**明确发现了这个补丁造成的污染**：
> *"the actual user message at the end contains what appears to be my instruction text?…meta-commentary about adding an ending"*

⇒ **一次机械补丁把"元指令"写进了正文，且审校环节察觉了却无力纠正**。

### 为什么 A2 / A6 留到下一轮（不做假承诺）

**A2（审校采样）** 不是"改个数字"，而是在**成本与召回之间做权衡**：

- 分段全量送审 ⇒ 每章审校的 token 消耗可能翻数倍，而本项目的瓶颈恰恰是**串行往返**；
- 只提高采样预算 ⇒ 缓解但不根除，仍是概率性漏检。

它需要**先有度量**（当前审校实际漏掉了多少结局问题？）才能定方案，
否则就是"凭感觉调参"。本轮已把该问题**原样登记**，不假装解决。

**A6（`add_relation` 零调用）** 属于本仓最高频的「注册即遗忘」模式，
但它的正确处理有两条路且**互斥**：要么接线、要么降级并改文档。
在没有确认"知识图谱关系是否真的能提升生成质量"之前接线，
只是把"没人调用的实现"变成"调用了但没效果的实现" —— 同样不诚实。

> 两条都在此**显式留痕**，避免"看起来都修完了"的错觉。
> 这正是本轮反复强调的：**登记缺陷要给可验证判据，不能给印象。**
