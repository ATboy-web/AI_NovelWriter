### 2.1 由核查得出的一个关键判断

> **这两个服务缺的不是「一个服务的骨架」，而是「整条链路」。**
>
> 认证服务要落地，需要从零补上：数据库访问层（目前完全不存在）→ 用户仓储 → 密码哈希与校验 →
> 令牌签发/刷新/吊销 → 接口层 → 测试。**这已经是「一个新产品」的工作量，而不是「补齐一个待办」的工作量。**

同时要注意 #9：**当前系统无法自行签发令牌**。这意味着即使有人按文档配好了 `SECRET_KEY`，
打开 `ENABLE_AUTH=true`，真实调用方**也拿不到合法 JWT**——只能靠静态 API Key。
这是一个必须先于立项被认知的事实（见 §7 前置阻塞项 P1）。

## 3. 需求侧分析：谁真的需要它？

| 交付形态 | 用户模型 | 是否需要认证服务 | 是否需要支付服务 |
|---|---|---|---|
| **桌面版**（主线，`novel_app.py`，PyInstaller EXE） | 单机单用户，本地文件即数据库 | ❌ 不需要 | ❌ 不需要 |
| **移动端 APK**（Compose，v4.0.1） | 单机单用户，用户自带 API Key | ❌ 不需要 | ❌ 不需要 |
| **自建单实例后端**（自用 / 小团队，compose 起栈） | 少量可信调用方 | ⚠️ **不需要独立服务**——静态 API Key 已实现且够用 | ❌ 不需要 |
| **多用户 SaaS**（注册、登录、订阅收费） | 互联网多租户 | ✅ 需要 | ✅ 需要 |

**判断**：前三种形态是**当前唯一已交付**的形态；第四种在多用户 SaaS 场景下才成立，而该场景
**目前既无产品规划落地，也无代码痕迹（前端零引用）**。

> 因此需求侧结论：**需求未成立**。为一个尚未确定的商业模式预先建设两个服务，属于典型
> 「投机性架构」（speculative architecture）。

## 4. 若立项：范围与工作量拆解

保留作为未来评审的输入。**本节不代表建议实施。**

### 4.1 认证服务 MVP

| 功能 | 必要性 | 说明 |
|---|---|---|
| 数据库访问层（连接池 / ORM / 迁移） | **必须** | 目前为 0，需从零建；含 Alembic 式迁移或 schema 版本管理 |
| 用户仓储（CRUD） | **必须** | 对应 `users` 表 |
| 密码哈希（bcrypt/argon2）+ 强度策略 | **必须** | 依赖 `passlib`/`bcrypt` 未安装 |
| 注册 / 登录 / 登出 | **必须** | 目前 0 接口 |
| 访问令牌签发 + 刷新令牌 | **必须** | 复用 `shared/middleware/auth.py` 的 `JWTManager`（已具备编码能力，仅缺调用方） |
| 令牌吊销 / 黑名单 | 建议 | 需引入 Redis（栈内已具备） |
| 邮箱验证 / 找回密码 | 建议 | 需邮件通道 |
| 角色与级别（`role` / `subscription_type`） | 建议 | 中间件已支持 `require_role` / `require_level`，数据侧需补齐 |
| 第三方登录（微信/GitHub） | 可选 | 依赖外部资质与审核 |
| MFA | 可选 | 后期 |

### 4.2 支付服务 MVP

| 功能 | 必要性 | 说明 |
|---|---|---|
| 订单 / 订阅模型与状态机 | **必须** | 对应 `subscriptions`、`payments` 表 |
| 支付渠道对接（微信支付 / 支付宝） | **必须** | 见 §5 合规风险 |
| 异步回调验签 + 幂等 | **必须** | 支付类系统的高危点，必须做对 |
| 对账 / 退款 | **必须** | 否则无法运营 |
| 订阅到期与自动降级 | **建议** | 与 `subscription_expires_at` 联动 |

### 4.3 工作量量级

| 项 | 认证服务 | 支付服务 |
|---|---|---|
| 新建/改动文件量级 | 数十个 | 数十个 |
| 新增容器 | +1 | +1 |
| 新增外部依赖/资质 | 邮件通道（可选） | **支付渠道商户资质（硬门槛）** |
| 新增测试面 | 高（安全敏感） | **极高**（资金敏感） |

## 5. 风险清单

| # | 风险 | 影响 | 缓解 / 说明 |
|---|---|---|---|
| R1 | **与已冻结的架构边界冲突** | 中 | `ARCHITECTURE_BOUNDARY.md` 明确「新增业务能力只在桌面端实现，后端不再扩展」。新建两个业务服务与该约定正面冲突，需先重新评审该约定 |
| R2 | **双份鉴权实现漂移** | 中 | 桌面端与后端已有各自的鉴权/配置逻辑；再加一个 auth-service 会形成第三份 |
| R3 | **支付合规与资质** | **高（阻塞级）** | 中国大陆收单必须经持牌支付机构（微信支付/支付宝/银联等），通常要求**企业主体 + 商户资质**。若项目以个人开源形态存在，**当前不具备收款路径**，这使支付服务在资质到位前无法交付 |
| R4 | **新增令牌签发面 = 新增攻击面** | 高 | 本项目刚刚修复「鉴权链 4 处叠加缺陷」（提交 `80ad0c3`，此前 `ENABLE_AUTH=true` 实际等同关闭）。在安全基线刚稳定时扩建认证面，风险收益比不佳 |
| R5 | **运维成本随服务数线性上升** | 中 | +2 容器 → 备份、监控（Prometheus/Grafana 需新增抓取目标）、升级、故障排查成本同步上升 |
| R6 | **数据库层从零建设的隐性成本** | 中 | 易被低估：连接池参数、迁移策略、连接泄漏、事务边界都需要工程经验，且现有测试体系（1246 passed）完全没有覆盖数据库层 |
| R7 | **空目录 + 文档误导的认知成本** | 低 | 已造成一次误判（`SECURITY_AUDIT_REPORT.md` 说「不存在」，README 说「存在」）。本次一并修正 |

## 6. 备选方案对比

| 方案 | 内容 | 成本 | 风险 | 建议 |
|---|---|---|---|---|
| **A. 独立双服务**（原规划） | 新建 `auth-service` + `payment-service`，各带 Dockerfile 并接入 compose | 高 | R1–R6 全中 | ❌ 现阶段不予采纳 |
| **B. 单服务内轻量模块** | 不新建服务，在 `novel-service` 中加 `/auth/*` 路由 + 复用 `shared/` 数据层 | 中 | 仍触及 R1、R4 | ⚠️ 仅当出现「少量可信用户」需求时作为第一步 |
| **C. 维持现状 + 补齐可用性缺口** | 不建服务；仅补「令牌签发入口」这一最小缺口，使现有 `AuthMiddleware` 真正可用 | **低** | 低 | ✅ **本次建议**（见 §7 P1） |
| **D. 删除空目录 + 文档正名** | 删除两个空目录，文档标注「规划中，未实现」 | **极低** | 极低 | ✅ **本次建议** |

**建议组合：C + D。** 即：**不建设服务**，但**消除文档误导**，并补上一个真正影响可用性的最小缺口
（令牌无签发方）。将来若触发 §8 的决策门，再按 §4 的范围从方案 B 起步、必要时演进到方案 A。

## 7. 前置阻塞项

无论将来选哪条路，以下问题都先于「立项」本身，属于**事实性缺陷**而非新功能：

| # | 阻塞项 | 现状 | 处置建议 |
|---|---|---|---|
| **P1** | **令牌无签发方**：`JWTManager.create_access_token()` 无任何生产调用者 | 开启 `ENABLE_AUTH=true` 后，调用方只能靠静态 API Key 通过；JWT 路径实际不可用 | 补一个最小的令牌签发入口（管理员用 `SECRET_KEY` 换取令牌，例如 CLI 或受保护的 `/api/v1/auth/token`），使 JWT 路径闭环。**这是本次建议唯一的代码动作，且可独立于立项** |
| **P2** | 数据库访问层完全不存在 | 0 命中 | 仅在立项启动后处理；届时应作为第一期唯一目标 |
| **P3** | `init.sql` 中 `admin` 的 `password_hash` 来源不明 | 固定 bcrypt 串，无人校验 | 核实是否为有效可用哈希；若无效则移除种子或改为安装时生成，避免「看起来有个管理员但登不上」 |
| **P4** | 静态 API Key 无吊销 / 轮换机制 | 靠环境变量 `API_KEYS` 字符串整体替换 | 文档中明确「改 key = 重启服务」的运维事实即可，暂不需建设 |

## 8. 决策门（重启立项的触发条件）

达到**任一**条件，即重启本评估：

| # | 触发条件 | 说明 |
|---|---|---|
| G1 | 产品上架应用商店 / 提供在线 SaaS，且需要**账号体系** | 多租户需求成立 |
| G2 | 出现**收费订阅**的产品决策，且**已完成企业主体与商户资质** | R3 解除，支付服务才有交付前提 |
| G3 | 单实例后端的使用者超过「可信小团队」规模（如外部用户 ≥ 30 人）或需按用户隔离数据 | 静态 API Key 的管理成本开始超过建设成本 |
| G4 | 需要第三方登录（微信 / GitHub）或多因素认证 | 认证服务的差异化价值出现 |
| G5 | 决定将后端从「可选形态」转为「主交付形态」 | `ARCHITECTURE_BOUNDARY.md` 约定随之重新评审（该文已预留此条） |

> 未达到上述条件前，任何 auth / payment 代码投入都属于**投机性建设**，应明确拒绝。
