# 回炉重造（章节级）

> 把**存量低质量章节**重新送进优化/重写流程：有入口、有判定、有状态、有存档、有结果。

| 项 | 值 |
|---|---|
| 核心模块 | `app/rework.py` |
| 面板 | `app/panels/rework_panel.py`（第 20 个面板，运维分组） |
| 数据目录 | `<作品>/rework/` |
| 状态数 | 7 |

---

## 一、它解决什么

软件侧的判定问题已经解决（质检门禁、评审判据、风格 DNA、一致性校验）。
但**已经写出来的那些章**还带着旧版判定留下的毛病 —— 全书性句式指纹、标题是占位符、
评审分从未记录 —— 而章节编辑区（`chapter_ui`）只有读写/导航/导出，
**没有"这章有问题，打回去重做"的位置**。

于是低质量章节永远停在原地：改完的判定管不到它们，作者也无法把"要重写"这件事
从脑子里搬进系统。

---

## 二、七个要素

### 1. 功能入口

面板「回炉重造」（运维分组 · 第 20 个），工具条四个动作：

| 动作 | 说明 |
|---|---|
| 扫描低质量章节 | 后台逐章跑质检（1094 章不会卡界面），结果进候选池 |
| 全部入炉 | 把候选批量入队（逐章跳过不适用项并计数） |
| 刷新 | 重读队列 |
| 双击行 | 让主编辑器打开该章（本面板不改正文） |

### 2. 适用范围

`ReworkStore.can_enqueue()` 在入炉前逐条判：

| 情况 | 结果 |
|---|---|
| 章节正文为空 | 拒绝（空章无从重写） |
| 已在「重写中 / 待审核」 | 拒绝（防止重复入队） |
| 已「定稿」 | 拒绝，除非强制（`force=True`） |
| 已回炉 ≥ `MAX_ATTEMPTS`（3）次 | 拒绝，需人工强制 |

扫描阶段另有 `min_hanzi`（默认 500 字）过滤残章，避免候选池被噪音淹没。

### 3. 触发条件

| 原因码 | 判定 | 与软件侧的关系 |
|---|---|---|
| `qc_blocker` | `qc_report()` 有**阻断项**（不含 review 项） | 与质检面板同源 |
| `low_score` | `review_store` 有记录且总分 < 阈值（默认 60） | 与评审同源；**没有记录不算低分** |
| `bad_title` | 标题缺失，或命中占位符（`第71章` / `章节标题(10字)`） | 独立判定 |
| `manual` | 人工指定 | 不参与自动扫描 |

三档自动判定是**互斥**的：标题有问题只报 `bad_title`，不再重复报质检项 ——
同一章在队列里出现两条记录会让"该改哪个"变得说不清。

`review` 项（粗筛项）**不能**驱动回炉：技能包明确允许"误报/指纹保留"，
拿它驱动会让队列被噪音灌满。

### 4. 状态流转

```
draft ──入炉──> pending_rework ──> reworking ──> pending_review
  ↑                  │                              │
  │                  │                              ├──> approved ──> published
  └──────────────────┴──────────────────────────────┴──> reworking（打回）
                     └──> discarded（任意处理中状态可废弃）
```

合法去向的唯一来源是 `rework.TRANSITIONS` 表：

```python
"draft":          ("pending_rework",)
"pending_rework": ("reworking", "discarded", "draft")
"reworking":      ("pending_review", "pending_rework", "discarded")
"pending_review": ("approved", "reworking", "discarded")
"approved":       ("published", "draft")
"published":      ("draft",)
"discarded":      ()          # 终点：要恢复就重新入炉，留痕
```

**刻意不允许** `draft → published`：那等于跳过重写与审核。
非法流转抛 `ReworkError`，附"允许的去向"；界面上对应按钮**置灰**
（界面置灰是体验，状态机校验是契约，两层都要有）。

### 5. 回炉原因记录

每条记录带四项：`reason_code`（可统计）、`reason_text`（人读）、
`evidence`（判定证据：命中的检测器、评审分、issues 摘要）、`attempts`（第几次回炉）。

`evidence` 不是可选的装饰：**没有证据的入炉等于"我觉得它不好"**，
过两周没人说得清当初为什么打回。

### 6. 原文与历史版本

- 入炉时**立刻**快照到 `rework/archive/chNNNN/v{n}.txt`，同目录有 `.meta.json`
  （字数 / 时间 / 备注）。
- 版本号 = 已有最大 + 1，**不覆盖**任何历史。
- `list_versions()` / `read_version()` 供面板回看。
- **快照放在入炉时而不是重写后**：入炉到重写之间用户可能还在主编辑器改这章
  （他还没意识到自己已经把它打回去了），快照放晚了就没有基线。

### 7. 处理结果

| 结果 | 状态 | 行为 |
|---|---|---|
| 审核通过 | `approved` | 可继续「定稿」或「退回正常」 |
| 定稿 | `published` | 视为完成；再入炉需强制 |
| 废弃 | `discarded` | **只改状态，不删任何文件**；原文与归档全部保留 |

`discard` 不提供"连归档一起删"的入口 —— 章节正文与角色库是同一量级的内容资产，
给"一键删干净"开口子的代价太大。

## 三、数据格式

`<作品>/rework/queue.json`：

```json
{
  "version": 1,
  "updated_at": "2026-11-18T09:09:00",
  "records": [
    {
      "chapter": 71,
      "status": "pending_rework",
      "reason_code": "bad_title",
      "reason_text": "标题缺失或为占位符",
      "evidence": {"title": "第71章"},
      "attempts": 1,
      "archive_path": "rework/archive/ch0071/v1.txt",
      "created_at": "...",
      "updated_at": "...",
      "history": [{"status": "pending_rework", "at": "...", "note": "入炉：标题缺失或为占位符"}]
    }
  ]
}
```

`history` 只追加，回答"这章是怎么走到现在这一步的"。

## 四、边界

| 不做 | 原因 |
|---|---|
| 不改正文文件 | 重写由主编辑器 / `novel_agent` 完成；本模块只管状态与存档 |
| 不重复实现质检 | 直接调 `qc_report()`，判定口径与软件侧同源 |
| 不做"一键全部重写" | 重写是 AI 调用，批量自动跑会把成本和风险一起放大；本模块只负责"排队"，执行由作者逐章决定 |
| 不删归档 | 见上 |

**"发布"在本项目里的含义**：AI_NovelWriter 没有平台发布通道，
所以 `published` 表示"本轮定稿，不再进回炉队列"。导出（TXT/EPUB/PDF/DOCX）
与云同步是独立功能，不受该状态限制。
