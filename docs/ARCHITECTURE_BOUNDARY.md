# 架构边界约定（P2-2）

本文件明确桌面端与后端的职责边界，冻结其中一端，避免「同一业务两套实现」的持续漂移。

## 结论：以桌面端为主线，后端为可选服务化实现（冻结后端业务扩展）

| 维度 | 桌面端（主线，Source of Truth） | 后端微服务（冻结，仅维护稳定） |
|------|-------------------------------|------------------------------|
| 入口 | `novel_app.py` + `app/` 包 | `backend/ai-service`、`backend/novel-service` |
| 定位 | 面向终端用户的完整产品 | 面向服务器/多用户的可选部署形态 |
| 业务逻辑 | 5-Agent 流水线、记忆系统、角色系统、写作工具 | `generators` / `consistency_checker` / `style_transfer` / `dialogue` / `story_flow` / `finalization` / `vector_store` |
| 迭代策略 | **持续演进**，新功能优先在此实现 | **冻结**：不再做与桌面端的功能对齐；仅接受缺陷修复与安全补丁 |
| 共享代码 | — | `backend/shared/`（两服务共享的 middleware，见 P2-3） |

## 约定细则

1. **新增业务能力只在桌面端实现**。后端不再追平桌面端的新特性，避免双份维护。
2. **后端仅在以下情况改动**：
   - 影响可用性的缺陷修复；
   - 安全漏洞（依赖 CVE、认证/限流/注入等）；
   - 部署与运维（Docker、CI、监控）。
3. **领域概念如需在两端一致**（如小说类型枚举），以后端 `generators` 中的 `NovelType`
   与桌面端 `app/` 中的定义为参照，改动时须同步并在 CHANGELOG 注明。
4. **共享层收敛于 `backend/shared/`**：两端服务共用的 middleware、后续公共配置等统一放此，
   服务侧仅保留薄转发层。

## 与之相关

- 优化清单 P2-2（前后端双实现）、P2-3（后端公共层抽取）。
- 若未来决定将后端作为主交付形态，本条约定需重新评审。
