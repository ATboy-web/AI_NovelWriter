## 0. `v3.1.0` 标签被重指三次（2026-09-17）

**事实**：v3.1.0 的标签今天移动过 3 次，依次指向 `fb83af1` → `cf0fa95` → `c55a9e9` → `fd69468`。

**原因**：每一次移动前，该标签的 CI 运行都**失败在发布作业上，没有产出任何 Release 或附件**，
所以不存在对外引用会被误导：

| 指向 | 该次 CI 的结果 | 失败原因 |
|---|---|---|
| `fb83af1` | Tests ×3 全红 | `app.__version__` 解析到 `backend/novel-service/app`（同名包劫持），版本一致性门禁失败 |
| `cf0fa95` | Tests ×3 全红 | 同上（第一版修正只改了"读哪个文件"，没解决"导入的是哪个包"） |
| `c55a9e9` | Tests 全绿，**Build EXE & Release 失败** | `release_notes.py` 在 cp1252 控制台打印中文崩溃（文件已写出，`Create Release` 被跳过） |
| `fd69468` | **全部 success** | 最终发布：`AI_NovelWriter.exe` 25,934,290 B |

**判断依据**：只有当"该标签从未发布过任何东西"时，重指才是纠正而不是篡改历史。
本文件的第 3 条（6 个标签指向同一提交）之所以**不处理**，正是因为那批标签**确实发布过**
Release 与附件 —— 两者的区别就在这里。

**若将来出现"标签已发布过却需要重指"的情况**：不要移动标签，改为**新版本号**并在正文里
说明；已发布的标签指向属于事实。

## 1. 9 个 Release 页面乱码（已修复）

**事实**：2026-09-17 排查发现，25 个 Release 里有 **9 个**的标题和/或正文被写成 `?`
（例如 `v2.14.0 - ??BUG??: ?????+?????`、`## ???? / - ??API????`）。
成因是早年发布工具在非 UTF-8 控制台下写中文。

**已做**：`scripts/fix_release_metadata.py` 逐条修复（幂等、可重复运行）。
还原依据有优先级，均为**可核实**的证据：

1. `CHANGELOG.md` 的对应条目；
2. 标签指向提交的 message（如 v2.7.0 的 `feat: v2.7.0 AI工程化升级 + 多项修复`）；
3. **乱码里 `?` 的个数保留了原文字数** —— 例如 `v2.14.1 - ??????` 是 6 个字符，
   与 CHANGELOG 该条目标题「角色空壳修复」的 6 字吻合；`GUI??(?????)` 的结构
   （GUI + 2 + 括号内 5）与正文 "Built with --windowed mode. No console window." 吻合。

**无法确证的一律不编造**：只给可核实说明，原始（乱码）文本放进 `<details>` 供追溯；
若原文已被覆盖取不回，换用另一个标记**如实说明"原文不可取回"**，绝不声称保留了它。

**例外（诚实记录）**：修复过程中 `v2.14.0` 的原始正文**被覆盖后无法完整取回**
（原因：补记脚本第一版的幂等性缺陷 —— 补记后的正文自己仍含 `??`，二次运行又套了一层）。
该 Release 现在使用"原文不可取回"的标记。教训已写进脚本与测试。

## 3. 六个标签指向同一提交（**未处理，保留待决策**）

**事实**：以下 6 个标签全部指向同一个提交 `0cf8c54`（2026-06-19）：

```
v2.12.1  v2.12.2  v2.12.3  v2.13.0  v2.13.2  v2.14.1
```

它们的 Release 分别在 2026-06-19 ~ 06-21 发布（附件多为 Android APK）。也就是说：
**这批发布并没有各自对应的代码快照**，而是共用同一个桌面端提交。

**为什么没有处理**：修正它意味着**改写标签指向**（`git tag -f` + 强推标签），而"每个版本
应当指向哪个提交"**没有可靠证据**（移动端与桌面端版本号本就并行演进，附件是 APK，
仓库里也没有对应的构建记录）。凭推测重指标签等于**伪造发布历史**，比保留现状更糟。

**若要处理，建议的姿势**（需仓库所有者决策）：

- 方案 A（推荐）：**保留现状**，仅在本文件记录 —— 历史事实就是这样，不必修正；
- 方案 B：删除这些标签，改用「发布说明」承载（Release 可脱离标签存在），
  但会让 `releases/tag/v2.12.1` 这类既有链接失效；
- 方案 C：为每个版本补一个**明确的说明**（正文里注明"该版本无独立代码快照"），
  不动标签、不改历史。

## 教训（两条，都真实付出过代价）

1. **"版本号是多少"必须由仓库回答，不能由运行环境回答。**
   `app/__init__._load_version()` 原先先查 `importlib.metadata`，于是环境里任何一份同名
   分发元数据都能覆盖真相（CI 上就是这样把 3.1.0 变成 1.0.0）。现已改为
   **pyproject.toml 优先**；同时 `tests/_app_authority.py` 把"`import app` 必须解析到仓库根"
   变成可断言的不变量 —— 本仓库有三个名为 `app` 的包，这条不变量不是洁癖。

2. **打印中文的脚本必须在入口切 UTF-8。**
   同一个坑踩了两次（`✓` 与 `已写入 …（N 字符）`），第二次直接导致发布失败。
   修复已抽成 `scripts/_console_utf8.py` 公共模块，并有三个针对 cp1252 流的回归测试。
   ⚠️ 这类失败**本地未必复现**（取决于本机控制台编码），且往往发生在"产物已经写好之后"
   —— 最难排查的那一类。
