# P4 面板层优化报告

> 日期：2026-09-16　基线：`525847e`
> 原则：**先量化，再优化**；每一项改动都保持原有意图与核心信息不变，并给出可复现的前后对照。

---

## 0. 怎么定方向：先测，不猜

优化前先写了测量脚本，对**真实规模**的数据（1094 章 / 11 个分页文件 / 300 个角色）跑一遍，
结果推翻了"应该没什么问题"的直觉：

| 场景 | 优化前 | 问题 |
|---|---|---|
| 时间线面板**一次刷新** | **48 次磁盘读取 / 68.0 ms** | 同一批 11 个分页文件被**重复读了 4 遍**（四个视图各读一次 + 摘要再读一次） |
| 传记面板**每选 1 个角色** | **23 次磁盘读取** | `character_tracks()` 全量扫描事件源；浏览 300 个角色 ≈ **6900 次**读取 |

而这两个动作都不是低频操作：`timeline.changed` / `chapter.saved` **每存一章就触发一次刷新**。

据此确定四个改进维度：**性能 → 结构 → 逻辑 → 可读性**，另附文档结构一处修正。

---

## 1. 性能：把"重复读"和"昂贵扫描"消掉

### 1.1 读取缓存（指纹失效，而非显式失效）

`TimelineStore` 增加按文件指纹的读取缓存，键是「分页文件的 `(名字, 大小, mtime_ns)` 元组」。

**为什么不用"写完清缓存"那种显式失效**：那要求**每个写入方**（`MemoryManager.add_event`、
`annotate_event`、`sync`，乃至将来任何脚本）都记得通知 store；漏一个就会看到过期数据。
指纹方案下，**任何**外部进程改动文件都会在下次读取时被发现 —— 正确性不依赖调用方的自觉。

代价是每次访问要枚举一次目录。这个代价被 1.2 压到可忽略。

### 1.2 目录扫描：`os.scandir` 替代 `glob + Path.stat()`

| 方式 | 耗时（11 个文件 / Windows） |
|---|---|
| `glob()` + `2×Path.stat()` | **5.96 ms** |
| `os.scandir()` + `entry.stat()` | **0.24 ms** |
| | **快 24.9 倍**，结果逐字节一致 |

原因：Windows 上 `DirEntry.stat()` 直接复用目录枚举已返回的数据，不再逐个发起系统调用。
新的 `_scan_dir()` **一次枚举同时给出"指纹"与"文件列表"**，于是缓存命中路径上只剩一次目录枚举。

### 1.3 一次取数（`snapshot()`）

新增 `TimelineStore.snapshot()`，一次返回四个视图 + 摘要；面板改为只调它一次。

两个收益：
- **一致性** —— 四个视图保证来自同一次读数，不会出现"章节轴已更新、人物轨迹还是上一秒"的撕裂；
- **成本** —— 面板层不再**有机会**重复读（即使将来有人去掉缓存也不会退化）。

### 1.4 面板层：复用实例 + 跳过无变化的渲染

- 时间线面板与传记面板各自**复用**一个 `TimelineStore`（换书时才重建）——
  缓存挂在实例上，复用才有意义；`novel_dir` 变化即重建，缓存不会跨书串味。
- `_fill()` 增加**行集指纹**：行内容没变就整体跳过重建。
  `chapter.saved` 每存一章都会刷新，而 1094 章的章节轴有 1094 行 ——
  每次重建 1094 行会让面板明显掉帧。

### 1.5 效果（同一脚本、同一数据规模）

| 指标 | 优化前 | 优化后 | 改善 |
|---|---|---|---|
| 面板刷新：磁盘读取 | 48 次 | **14 次** | −71% |
| 面板刷新：耗时 | 68.0 ms | **22.6 ms** | **−67%** |
| 每选一个角色：磁盘读取 | 23 次 | **0 次**（命中缓存） | −100% |
| 选 20 个角色：耗时 | 567 ms | **19.3 ms** | **−97%** |

优化后刷新耗时的主体已经是**首次 JSON 解析**（11 个分页 × 100 条），不再有可省的部分。

## 2. 结构：让"取数"与"渲染"分开

优化前 `reload()` 里是五句并列的取数语句：

```python
axis = store.chapter_axis()
...
self._fill(..., branch_rows(store.branch_tree()))
self._fill(..., track_rows(store.character_tracks()))
self._fill(..., chronicle_rows(chronicle))
self._set_stats(stats_text(store.stats()))
```

五句话本身没错，但它们**各自隐含一次完整取数**，读代码的人看不出成本在哪，也就不会警觉。
改成一次 `snapshot()` 之后，"面板刷新 = 一次取数 + 四次渲染"成了**写在结构里的约束**，
而不是靠注释提醒。

同时把 `stats()` 里重复的统计逻辑抽成 `_stats_from(events, tracks)`，
让 `snapshot()` 与 `stats()` 共用同一份算法 —— 两处口径不会再分叉。

## 3. 逻辑：缓存带来的正确性风险，用测试钉住

缓存最大的风险是"返回过期数据"。因此新增 **16 个**测试专门验证：

- 缓存命中确实不碰磁盘（用计数包装 `read_json_with_backup` 断言）；
- **外部写入立刻可见**：绕开 store 直接写分页文件 / 写 `character_activity.json`，下次读取必须看到新内容；
- 指纹对**新增分页**、**删除分页**、**同文件内容变化**都敏感；
- `invalidate()` 能强制重算；不同实例缓存互不影响；
- `snapshot()` 与逐个视图取到的结果**逐项相等**（"一次取数"不能改变语义）。

另外顺手修正了一处**真实缺陷**（见 `CODE_REVIEW_P4.md` §2 A3）：
`lineage_panel` 里 `lin.read_lineage(x)` 被调用两次且可能解引用 `None`，
且"继承用已登记父代、年龄换算用下拉框当前项"会导致两条路径指向不同父代。

## 4. 可读性：注释只写"为什么"

本次改动的注释一律回答"为什么这么做"，而不是复述代码：

- 为什么用指纹而不是显式失效（§1.1 的理由写进了类文档）；
- 为什么 `_scan_dir` 值得单独存在（附 24.9 倍的实测数字）；
- 为什么面板要复用 store（附"6900 次读取"的实测）；
- 为什么 `_fill` 要做指纹比对（附"1094 行 × 每章一次"的算子）。

理由：**数字比形容词更能阻止后来者把它改回去**。

## 6. 明确**没有做**的优化（避免过度优化）

| 候选 | 为什么不做 |
|---|---|
| 给 `read_world_line()`（单条）也加缓存 | 它被 `sync()` 用于写前读，必须拿到**最新**内容；加缓存反而制造"用旧内容覆盖新文件"的风险 |
| 用"写完清缓存"替代指纹 | 依赖所有写入方自觉，漏一处就是过期数据（§1.1） |
| 把指纹改成"只比目录 mtime" | 只加/删文件才改目录 mtime；**同文件内容变化不会被发现** ⇒ 会返回过期数据 |
| 章节轴虚拟滚动 / 增量更新 Treeview | 已用行集指纹把"无变化时重建"消除；再做增量更新需自维护行与 iid 的映射，复杂度与收益不成比例 |
| 把 `stats()` 改成纯 `snapshot()` 的别名 | `stats()` 是面板之外（脚本/自检）也会用的窄接口，保持它只做统计、不触发四视图计算 |
