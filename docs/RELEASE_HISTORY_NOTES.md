# 发布历史异常记录

**文档日期**：2026-09-17　|　**状态**：已处理 3 项，保留 1 项待决策

本文件记录仓库发布历史里**已知的、无法靠常规手段自愈**的异常，避免后来者反复排查
同一件事。每一条都写明「事实」「已做的处理」「为什么没有进一步处理」。

## 1. 9 个 Release 页面乱码（已修复）

**事实**：2026-09-17 排查发现，25 个 Release 里有 **9 个**的标题和/或正文被写成 `?`
（例如 `v2.14.0 - ??BUG??: ?????+?????`、`## ???? / - ??API????`）。
成因是早年发布工具在非 UTF-8 控制台下写中文。

**已做**：`scripts/fix_release_metadata.py` 逐条修复（幂等、可重复运行）。
还原依据有优先级，均为**可核实**的证据：

1. `CHANGELOG.md` 的对应条目；
2. 标签指向提交的 message（如 v2.7.0 的 `feat: v2.7.0 AI工程化升级 + 多项修复`）；
3. **乱码里 `?` 的个数保留了原文字数** —— 例如 `v2.14.1 - ??????` 是 6 个字符，
   与 CHANGELOG 该条目标题「角色空壳修复」的 6 字吻合；`GUI??(?????)` 的结构
   （GUI + 2 + 括号内 5）与正文 "Built with --windowed mode. No console window." 吻合。

**无法确证的一律不编造**：只给可核实说明，原始（乱码）文本放进 `<details>` 供追溯；
若原文已被覆盖取不回，换用另一个标记**如实说明"原文不可取回"**，绝不声称保留了它。

**例外（诚实记录）**：修复过程中 `v2.14.0` 的原始正文**被覆盖后无法完整取回**
（原因：补记脚本第一版的幂等性缺陷 —— 补记后的正文自己仍含 `??`，二次运行又套了一层）。
该 Release 现在使用"原文不可取回"的标记。教训已写进脚本与测试。

（标签从 `v2.14.3` 直接跳到 `v2.16.0`）。

**已做**：定位到提交 `c0aa0b7`（`v2.15.0: 写作技能系统 + Token统计 + 全面代码审查`，
与 CHANGELOG 条目内容一致），用 `git merge-base --is-ancestor` 确认其在 `main` 上之后
补打标签并推送。**未创建对应 Release**（避免凭空补一份发布说明）。

## 3. 六个标签指向同一提交（**未处理，保留待决策**）

**事实**：以下 6 个标签全部指向同一个提交 `0cf8c54`（2026-06-19）：

```
v2.12.1  v2.12.2  v2.12.3  v2.13.0  v2.13.2  v2.14.1
```

它们的 Release 分别在 2026-06-19 ~ 06-21 发布（附件多为 Android APK）。也就是说：
**这批发布并没有各自对应的代码快照**，而是共用同一个桌面端提交。

**为什么没有处理**：修正它意味着**改写标签指向**（`git tag -f` + 强推标签），而"每个版本
应当指向哪个提交"**没有可靠证据**（移动端与桌面端版本号本就并行演进，附件是 APK，
仓库里也没有对应的构建记录）。凭推测重指标签等于**伪造发布历史**，比保留现状更糟。

**若要处理，建议的姿势**（需仓库所有者决策）：

- 方案 A（推荐）：**保留现状**，仅在本文件记录 —— 历史事实就是这样，不必修正；
- 方案 B：删除这些标签，改用「发布说明」承载（Release 可脱离标签存在），
  但会让 `releases/tag/v2.12.1` 这类既有链接失效；
- 方案 C：为每个版本补一个**明确的说明**（正文里注明"该版本无独立代码快照"），
  不动标签、不改历史。
