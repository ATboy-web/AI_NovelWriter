# 硬件资源加速与卸载方案（v1，2026-09-17）

> **目标**：把「应用卡顿」从感受变成可归因的数字，再决定哪些环节该卸载到 CPU/GPU。
> **前提**：本机实测硬件为 **i5-12490F（12 逻辑核）+ RTX 3080（10 GB 显存，驱动 610.47）**，
> 已有 Ollama（`~/.ollama/models` 占 **27 GB**，装了 3 个模型）。
> **口径**：所有「当前状态」判断均来自仓库实测（`文件:行号` 或命令输出），不引用文档说法。

---

## 0. 先纠正一个前提：现在的卡顿**不是**算力不够

这是本方案最重要的一句话。在动手调 GPU 之前必须先说清楚：

**本项目的瓶颈是「等待」与「无谓重复」，不是「计算量」。**

依据（全部来自实测）：

| 事实 | 证据 |
|---|---|
| 生成一章 = **5 段串行 + 最多 3 轮修订**，每段一次网络往返 | `novel_agent.py:643-758`。AST 实测各段的 `ai.chat()` 次数见下表 |
| **单章最少 3 次、最多 9 次网络往返** | 主流程 3 次必发（`_plot_designer_analyze` + `_writer_generate` + 每轮 `_reviewer_evaluate`）；`for round_num in range(1, MAX_REVISION_ROUNDS+1)` 且 `MAX_REVISION_ROUNDS = 3`（`:152`），每轮若评分 < `QUALITY_THRESHOLD = 75`（`:151`）则追加一次 `_writer_revise` |
| 33 个 AI 调用点**全部是阻塞式 `chat()`**，无一使用流式 | 全仓 `chat_stream` 仅 3 处命中，**全是定义/文档字符串，生产零调用**；`ai.chat(` 有 33 处 |
| 诊断日志**不记录耗时** | `diagnostic-2026-09-17.jsonl` 的 `API_CALL` 事件只有 `provider/endpoint/request/response`，**没有 latency 字段** |
| 单章延迟的量级由**模型推理时间**决定 | 用的是 `deepseek-v4-pro` / `gpt-4o` / `claude-sonnet-4` 等云端大模型，单次往返秒级到十几秒 |

**AST 实测的各段网络往返数**（`ast` 静态统计 `ai.chat()` 调用点）：

| 方法 | 行号 | `ai.chat()` 次数 | 说明 |
|---|---|---|---|
| `_plot_designer_analyze` | `760-788` | **1** | 情节分析，必发 |
| `_world_builder_build` | `790-799` | **0** | ⚠️ **不发网络请求**，只读本地 `settings` 并返回（`known` 为空时直接返回 `""`） |
| `_build_context` | `345-481` | **0** | 纯本地上下文组装 |
| `_writer_generate` | `801-893` | **1** | 正文生成；若走长章分支则转 `_generate_long_chapter` |
| `_reviewer_evaluate` | `895-977` | **1** | 每轮审校，**循环内必发** |
| `_writer_revise` | `979-1063` | **1** | 仅在评分不达标时追加 |
| `_generate_long_chapter` | `2063-2175` | **2** | 长章分段生成（额外一次） |

> ❗ **上表纠正了一个常见的误读**：`_world_builder_build` 与 `_build_context` 听起来像重活，
> 实测**一次网络请求都不发**。所以"5 个 Agent"里真正出网的只有 **3 个**
> （PlotDesigner / Writer / Reviewer）。**讨论优化时必须按实际出网次数算，不能按 Agent 个数算。**
>
> **推论**：一次 5 Agent 协作生成，用户等待时间 = **3–9 次 ×（网络往返 + 远端推理）**，
> 这个总量级是**几十秒到几分钟**。而 GPU 能加速的是「本地计算」——
> 本项目里本地计算占比极低，**直接上 GPU 对主流程几乎零收益**。
> 真正立刻见效的是下面 T1/T2 两条（纯 CPU 与工程改造，不需要 GPU）。

**因此本方案的组织方式是：先卸掉「假的卡顿源」，再谈真需要硬件的场景。**

## 3. 真正的加速手段（按投入产出比排序）

### T2 流式输出上主流程 —— **最高性价比，不需要任何新硬件**

**现状**：`chat_stream()` 在 `ai_client.py:1223` **已完整实现**，含
`adapter.parse_stream_chunk()` 的多厂商 SSE 解析（`:1250-1293`），**且有测试**。
但 **33 个调用点全部走阻塞 `chat()`，流式零使用** —— 教科书级「注册即遗忘」。

**收益**（体感层，而非吞吐层）：

| 指标 | 现状（阻塞） | 流式后 |
|---|---|---|
| 首个字出现时间 | = 完整生成时间（数秒~十几秒） | **TTFB ≈ 0.3–1 s** |
| 用户能否判断"卡死了" | ❌ 只能干等 | ✅ 立刻看到在写 |
| 能否中断 | 只能等完 | ✅ 可随时停 |
| 总裁时长 | 相同 | **相同**（不省时间） |

> ⚠️ **必须诚实说明取舍**：流式**不减少总耗时**，它改的是**感知延迟**。
> 而对「卡顿」这个抱怨，感知延迟往往才是主因。这是全方案里
> **改动最小、见效最快、零新增依赖**的一项。

**实施要点**：桌面端 Tk 非线程安全，流式回调必须经
`app/async_runner.py` 的 `BackgroundRunner` 把 chunk 投递到主线程
（**不可直接在子线程更新 Text 控件**）。`fullscreen_writer.py:434/625` 是最值得先改的两处。

### T3 CPU 并行：**先划掉这一项**（实测证明无从并行）

> **⚠️ 本节在撰写过程中经 AST 实测后自我否决。保留在此是为了留下"为什么不做"的证据 ——
> 避免下一个人重新提同样的方案。**

**原假设**（错误）：`_plot_designer_analyze` 与 `_world_builder_build` 都只依赖章节大纲，
可以并发，省一次往返。

**实测结论**：
1. `_world_builder_build`（`novel_agent.py:790-799`）**根本不发网络请求** ——
   它读一下 `settings["world"]["已知区域"]` 就返回字符串，`known` 为空时直接返回 `""`。
   它**没有往返可省**。
2. `_world_builder_build` 虽然签名收着 `plot_analysis`，但函数体**完全没使用该参数**
   （形参是死的）—— 这说明当初的 5-Agent 设计里 WorldBuilder 本应是独立 LLM 调用，
   **实现时被简化成了本地查表**。
3. 真正出网的 3 段（PlotDesigner → Writer → Reviewer）是**严格串行依赖**：
   Writer 需要 `plot_analysis`，Reviewer 需要 `content`。**没有任何一对可以并发。**

**结论**：**本项目单章生成链上不存在可并行的网络调用。** T3 作废。

> **可复用的判据**：讨论"能不能并行"时，必须先用 AST 确认**到底哪几段真的出网**，
> 而不是看有几个 Agent/几个方法名。本次若不做这一步，就会写出一个
> "并行两个不存在的请求"的方案。

**那么 `ThreadPoolExecutor(max_workers=3)`（`agent_orchestrator.py:19`）用在哪？**
它服务于 `agent_orchestrator` 自己的多 Agent 编排路径（与 `novel_agent` 的
`generate_with_collaboration` 是两条不同入口）。**该处的并行是否正确、是否必要，
本轮未验证**——登记为待查项，不在本方案主张范围内。

### T4 本地推理卸载到 GPU —— 唯一真正"用上 GPU"的场景，但有硬约束

**这是用户提问中最关心、但对本项目最需要谨慎的一项。**

Ollama 装在 `C:\Users\Administrator\AppData\Local\Programs\Ollama\ollama.EXE`，
模型已就位。`app/providers/ollama.py` 已有适配器 ⇒ **接入路径是通的**。

**但实测显存给出了硬约束**：

| 模型 | 体积 | 10 GB 显存能否全量加载 | 结论 |
|---|---|---|---|
| `qwen3.6-35b` | 11.66 GB | ❌ **超了 1.3 GB** | 会溢到系统内存 ⇒ **比不加速更慢**（CPU/GPU 反复搬运） |
| `qwen3.6-35b-vision` | 12.56 GB | ❌ 超 2.3 GB | 同上 |
| `darkidol-8b` | 16.07 GB | ❌ 超 6 GB | 同上（应为 FP16 未量化） |

> 🔴 **关键结论**：**现装的 3 个模型没有一个能在 10 GB 显存上全量驻留。**
> 若直接切到 Ollama + 现有模型，**大概率比云端 API 更慢**，
> 会被用户判定为"优化失败"。这是必须先讲明的风险，而不是等踩坑。

**正确做法（若坚持走本地 GPU）**：
1. 换**量化版本**（Q4_K_M 级别）：35B 量化后约 **20 GB** 仍超；
   ⇒ 实际可行的是 **7–8B 的 Q4 量化**（约 4–5 GB），或 **14B 的 Q4**（约 8–9 GB）留出 KV cache 余量。
2. 用 `nvidia-smi` 确认实际驻留（`ollama ps` 会显示 `100% GPU` / `partial`）。
3. **只看 `eval rate`（tok/s）**，不看是否"用了 GPU"。

**收益预期**：7–8B Q4 在 3080 上约 **40–80 tok/s**。
但**质量与 `deepseek-v4-pro`/`claude-sonnet-4` 差距明显**，
对「长篇小说一致性」这类高要求任务，**质量损失很可能大于速度收益**。

**适用条件（三者同时满足才建议用本地 GPU）**：
- 任务对质量不敏感（如：**批量生成章节摘要、抽取角色名、格式转换**等辅助工作）；
- 有网络隔离/隐私/成本诉求（本地零费用、数据不出机）；
- 单次上下文不超模型窗口（否则显存被 KV cache 吃掉）。

**取舍**：本地 GPU = **省成本 + 快 + 保隐私**，但**降质量**。
合理架构是**分工**而非替换（见 T5）。

### T5 混合路由：贵模型写作，本地 GPU 干杂活

把 T4 的取舍转化为架构优势：

| 环节 | 模型 | 理由 |
|---|---|---|
| 情节设计 / 正文创作 / 审校 | **云端大模型**（现有配置） | 质量敏感，不可妥协 |
| 章节摘要、角色名抽取、EXP 事件识别、格式转换 | **本地 7–8B Q4（GPU）** | 高频、低价值、可容忍质量波动；**零 token 成本** |

> 依据：`app/parsing.py` / `token_estimator.py` 等辅助环节调用频繁但要求低。
> 这能把本地 GPU 的 27 GB 模型**真正用起来**，且不伤害主流程质量。

### T6 CPU 侧：把文档解析搬出主线程

`format_converter.py:266/411` 用 `ebooklib` / `python-docx` 解析整本书；
`reading_manager.py:24/31/41` 读 PDF/EPUB/DOCX。这些是**真 CPU 密集**（纯 Python 解析），
若在 UI 线程执行会**直接冻结界面**。

- **方案**：搬到 `BackgroundRunner`（已有统一执行器）+ 给大文件加进度回调。
- **收益**：消除"打开大书时界面假死"。
- **注意**：`ebooklib`/`python-docx` 是**纯 Python**，**多进程（multiprocessing）才可能真并行**；
  但进程启动/序列化开销大，**短任务反而更慢** ⇒ 先测量再决定，**不要预设**。

## 5. 适用条件与限制（统一说明）

**通用限制**

1. **显存 10 GB 是硬顶**。占满会导致驱动换页，性能崩塌而非下降。
   所有 GPU 方案都须留 ≥ 1.5 GB 给 KV cache 与桌面。
2. **网络延迟无法用硬件消除**。云端往返是物理距离，本地 GPU 只能"绕过"（换模型），不能"加速"。
3. **Python GIL**：多线程不能并行纯 Python 计算。本项目主要收益来自
   **I/O 并发**（有效）而非 CPU 并行（无效）。
4. **增加依赖即增加分发体积**。`pyproject.toml:22-28` 曾把 `chromadb` 移出强制依赖，
   理由正是"每个用户被迫装数百 MB 却永不使用" ⇒ **GPU 相关依赖必须走 optional extra**，
   不得进 `dependencies`。

**分项限制**

| 方案 | 硬性条件 | 失效情形 |
|---|---|---|
| T2 流式 | 供应商支持 SSE（openai/claude/ollama 均已适配） | 部分自建网关可能不支持；需回退到 `chat()` |
| ~~T3~~ | — | **已作废**（无可并行项） |
| T4 本地 GPU | **模型量化后 ≤ 8.5 GB**；CUDA 驱动正常 | 模型超限 → 溢出 → **比不加速更慢** |
| T6 多进程 | 任务足够大（进程启动开销需被摊薄） | 小文件场景**负收益** |

## 6. 实施顺序（每步的产出作为下一步输入）

```
T1 埋点 + 基线          ← 必须先做，否则后面全靠猜
   ↓ 产出：各环节耗时分布（含 3–9 次往返各占多少）
T2 流式上主流程          ← 不依赖基线，可并行开工（零风险、零新依赖）
   ↓ 产出：体感改善 + 更细的 TTFB / 完成时间
T4/T5 本地 GPU 分工      ← 仅在 T1 基线证明"辅助调用占比高"时才值得
   ↓
T6 文档解析后台化
```

**建议的最小起步集**：**T1 + T2**。两者都不需要 GPU、不改架构、
不动 `backend/`（冻结中），且能同时改善**可观测性**与**用户体感**。
做完再拿数据决定是否投入 T4–T6。

**（T3 已作废，不进入顺序）**

## 8. 一句话总结

**先用 T1 把卡顿变成数字，用 T2 把等待变成"看得见在写"；
GPU 只在「低价值辅助任务」上有位置（且必须先解决现装模型超出 10 GB 显存的问题）。
不建议为了"用上 GPU"而引入 torch —— 本项目没有可被 GPU 加速的本地计算。**

## 9. 本方案的自我修正记录

本文件在撰写与实施过程中**两次推翻了自己的结论**，留档以免后人重犯：

| 原判断 | 实测结论 | 修正依据 |
|---|---|---|
| T3「PlotDesigner 与 WorldBuilder 可并发，省一次往返」 | **作废**：`_world_builder_build` 不发网络请求（`novel_agent.py:790-799`），且出网 3 段严格串行 | `ast` 静态统计各方法内 `ai.chat()` 调用数 |
| 「5 个 Agent 各一次往返」 | 实际 **3 段出网、单章 3–9 次往返** | 同上 |
| T1.1「诊断日志没有耗时字段，要在 `ai_client` 铺垫计时」 | **作废**：字段一直在（`diagnostic_logger.py:130`），出口记录也一直在传（`ai_client.py:945`）。真缺口是**章节级归因缺失**+**测试污染** | 读源码 + 统计真实日志（`CHAPTER` 事件 3 天内 **0** 条） |

> **教训一**：判断"哪几段出网""能不能并行"**不能看方法名或 Agent 数量**，
> 必须用 AST 数调用点。本次若跳过这一步，会写出一个"并行两个不存在的请求"的方案。
>
> **教训二**：**"我认为缺什么"必须去读代码确认**。初版 T1.1 凭印象断言"没有耗时字段"，
> 实际字段与调用都在，只是**记的东西不是我们需要的**（记 API 往返，没记章节分段）。
> 凭印象写方案会凭空造出一堆不需要改的改动，而真正该改的被漏掉。
>
> **教训三**：**观测能力"建了一半"比没建更危险**。`DurationLogger` 早就支持
> `duration_ms`、`chapter_event()` 也早就存在，但生成主流程从不调用 ——
> 于是日志看着很丰富，却回答不了唯一重要的那个问题（"这一章为什么慢"）。
> 判断观测是否可用，标准是"**能否回答一个具体的决策问题**"，不是"字段是否存在"。
